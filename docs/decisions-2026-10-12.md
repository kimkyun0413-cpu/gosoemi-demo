## 최우선: 개인정보처리방침과 실제 AI 처리의 불일치

### 무엇이 다른가
- 시행 중인 방침(v2): "Google Gemini API(유료 API)… 입력·응답은 제품 개선(모델 학습 포함)에 사용되지 않으며"
- 실제: 운영 키가 **무료 등급** → Google 약관상 입력·응답을 제품 개선에 쓰고, 사람 검토자가 읽을 수 있으며, "민감·기밀·개인정보를 보내지 말라"고 함
- 해당 처리: 일반 이용자의 AI 상담, 고소장 초안 만들기(사건 내용 전체). 증거파일은 Gemini로 보내지 않음. 운영 DB 사건은 7건(2026-10-11 기준, 시험 계정 포함)

### v3 시행까지 미루면 안 되는 이유
- 차이는 방침 문구가 아니라 **실제 처리 방식**에 있음. v3도 '유료 API'라고 적고 있어, 시행해도 무료 등급이면 그대로 틀림
- 무료 등급에 개인정보를 보내는 것 자체가 Google 약관과 맞지 않음

### 대응안
| 안 | 내용 | 효과 | 비용 | 추천 |
|---|---|---|---|---|
| ① 유료 전환 | 결제 연결 + 선불 | 전환 뒤 처리는 방침과 일치(학습·사람 검토 없음) | 쓴 만큼(아래 A) | **예 — 가장 먼저** |
| ② AI 잠시 멈춤 | `AI_FEATURES_PAUSED="true"` (준비 완료, 운영 미적용) | 전환 전까지 새 전송을 막음. 사건 저장·내 사건·내려받기는 그대로, 저장한 사건은 나중에 초안 만들기 가능 | 없음 | **①을 오늘 못 하면 즉시** |
| ③ 방침을 '무료 등급'으로 고치기 | 사실대로 적는 새 버전 | 문구는 맞지만 약관상 개인정보를 보내면 안 되는 상태는 그대로 | 없음 | 아니오 |
- 이미 무료 등급으로 처리된 자료는 Google에서 지울 수 없습니다. 이용자 안내·신고가 필요한지는 법률 판단이 필요합니다(검토 자료 질문 14).

## A. Gemini 유료 전환 — 절차·비용 (공식 문서 2026-10-12 확인)
### 절차 (운영자가 직접)
1. Google AI Studio → 'Projects'(또는 'API keys') 화면 → 'Default Gemini Project' 줄의 **Set up billing**
2. Cloud 결제 계정 선택 또는 새로 만들기(국가·연락처·결제 수단)
3. **선불 최소 $5 충전**(계정에 따라 선불/후불 선택이 다를 수 있음). 선불 크레딧은 12개월 뒤 만료, 대체로 환불 불가
4. AI Studio → **Spend** → 'Monthly spend cap' → 월 지출 한도 입력(예: $10)
5. AI Studio 프로젝트 목록에서 등급이 바뀐 것 확인 → 저에게 알려 주시면 할당량 화면으로 다시 확인
- 앱 설정(키)은 바꿀 필요 없음: 같은 프로젝트·같은 키가 유료가 됩니다.

| 선불 잔액 | **예** | 잔액이 $0이 되면 요청이 402 오류로 실패(자동 충전을 켜지 않으면) |

### 3. Gemini 이용 연령 조건
- Gemini API 추가 약관 'Age Requirements'(2026-04-28): API 이용자는 18세 이상, **18세 미만이 대상이거나 이용할 가능성이 높은 서비스에서 쓰지 않는다**.
  적용 범위는 Gemini API 전체 → 고소미의 AI 상담·초안·음성 받아쓰기·입력칸 정리·요약·표현 바꾸기·서버 목소리 **모두 해당**.
- Google Cloud(Vertex AI) 서비스 약관 20(d)도 같은 내용 → 옮겨도 해결되지 않음. 위반이 의심되면 바로 중지될 수 있음(20(f)).

### 4. 메일 인증·비밀번호 찾기 — **이메일 가입이 일반 이용자에게 사실상 막혀 있음**
- 운영 Supabase: 새 가입 허용, **'Confirm email'(이메일 인증) 켜짐**, 직접 메일 서버(SMTP) 없음 → Supabase 기본 메일 사용.
- Supabase 공식 문서: 기본 메일은 **프로젝트 팀원 주소로만 보내고**(그 밖의 주소는 거부), 시간당 2통, 운영용 아님.
- 그래서 일반 이용자가 이메일로 가입하면 인증 메일을 받지 못해 로그인할 수 없습니다. 네이버·Google 로그인은 영향 없음.
- 비밀번호 찾기는 꺼져 있음(`PASSWORD_RESET_ENABLED`). 메일 서버가 있어야 켤 수 있음.
- 이번에 한 일: 메일을 못 보낼 때 "네이버 또는 Google로 가입해 주세요"라고 알리도록 고침. 운영자가 이메일 가입만 잠시 닫을 수 있는
  `EMAIL_SIGNUP_ENABLED` 설정 추가(설정이 없으면 지금처럼 열림 — 운영 설정은 바꾸지 않음).

### 5. 백업·복구 — **스크립트 오류 2개 발견·수정**
- 로컬 임시 DB에서 백업 → 새 DB에 복구까지 처음으로 실제 실행(`supabase/tests/local_backup_restore_test.py`, 17/17 통과).
- 발견 1: 백업 스크립트가 **계정 표만 담고 사건·초안·동의·네이버 연결 자료를 빠뜨림**(pg_dump는 `--table`을 쓰면 `--schema`를 무시). 운영에서 실행한 적이 없어 불완전한 백업은 없음. 고침.
- 발견 2: 복구가 'public 스키마가 이미 있음'으로 첫 줄에서 멈춤(새 Supabase 프로젝트에는 public이 있음). 고침(예전 백업 파일에도 적용).
- 확인: 행 수 일치, 계정-사건 연결, 본인만 보는 정책 유지, 틀린 암호·운영 주소로는 복구하지 않음, 백업 파일에 자료가 평문으로 보이지 않음.
- 아직: 운영 DB에서 실제 백업, 새 Supabase 프로젝트에 복구 연습(실제 auth 표 구조로), 증거파일 백업 실행.

### 6. 결제 준비 — 변화 없음
- 판매 꺼짐(`BILLING_MODE` 없음 = off). DB·Edge Function 안은 적용 안 함. 웹훅 처리 테스트 8개 통과(오늘 다시 실행).
- 사업자등록·통신판매업 신고·결제사 계약 전에는 진행할 것 없음.

### 7. 운영 설정에 쓰이지 않는 비밀값
- `SUPABASE_SECRET_KEY`: IP 전달 설정이 꺼져 있어 지금 코드에서 쓰지 않음(전체 권한 키라 두지 않는 편이 안전).
- `APP_PASSWORD`: 지금 코드 어디에서도 쓰지 않음(예전 설정으로 보임).
